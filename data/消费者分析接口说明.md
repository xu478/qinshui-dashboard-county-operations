# 消费者分析自动刷新接入

## 当前需求：先计算实际10天并回放

本期先使用9月24日至10月3日的真实会员订单，首尾10天。页面显示“平均消费频次”和“期间复购率”，保留两位小数；不把这批数据称为30日指标。默认以9月24日至10月1日正额会员订单为初始统计，再按已核验的内置10月2日、3日订单顺序渐进加入。会员编码仅在私有处理内存中用于去重与累计，不写入公开JSON。

运行本期处理器：

```sh
python build_consumer_replay_metrics.py \
  --input /server/private/pos-order-headers.xlsx \
  --events-json /site/data/today-replay-orders.json \
  --coverage-start 2026-09-24 --coverage-end 2026-10-03 \
  --end 2026-10-03 --replay-start 2026-10-02 --days 10 \
  --snapshot-output /site/data/consumer-metrics.json \
  --replay-output /site/data/consumer-replay-metrics.json
```

公开snapshot只含完整期间人数/单量汇总；replay JSON只含初始计数、每个回放步数对应的聚合计数、末值及版本指纹。SHA256由公开回放订单按现有顺序的`[key,amountCents]`紧凑JSON计算，严格核验与私有源中的原付款日/门店/流水、金额和完整事件集一致；不输出原始身份字段。匿名与负额订单不增加会员购买数；同一笔重复滚动展示不会重复累计。

完整10天为2,027笔会员正额订单、818个购买会员、425个多次下单会员，计算值2.48次/统计期、51.96%。回放中间值表示“8天历史＋已经处理的后两天会员记录”，原始日期不映射为今日，也不代表今日新增会员。进行中的回放不被后台整期刷新覆盖；停止回放则恢复实际完整期间汇总。人工新导入未提供可核验会员聚合映射时，不猜测购买人数，仍显示已提供的历史期间汇总。

## 通用30天处理器

`build_consumer_metrics.py` 把后端私有的 POS 订单头 `.xlsx` 转换为公开聚合 JSON。页面轮询该 JSON，源数据处理程序在每次获得新导出后重新运行即可；这属于源数据更新能力，尚未配置定时任务或后台 ERP 推送。源表、会员编码、姓名、电话均不进入公开输出。

使用 Python 3.10+ 和 `openpyxl`。一次只输入一份订单头导出，不合并实物商品明细，也不叠加相同流水的 ERP 副本。以首 20 行中唯一包含 `流水号`、`门店编码`、`会员编码`、`收款日期`、`实收金额` 的表头定位数据；多个匹配工作表会停止计算。

```sh
python build_consumer_metrics.py \
  --input /server/private/pos-order-headers.xlsx \
  --coverage-start 2026-09-24 \
  --coverage-end 2026-10-03 \
  --end 2026-10-03 \
  --output /site/data/consumer-metrics.json
```

通用处理器默认 `--days 30`，截至业务日 `2026-10-03` 的窗口为 `2026-09-04`～`2026-10-03`，首尾均包含。因此上例只有10天的真实覆盖，按30天要求会输出 `status: "unavailable"`、`window.complete: false`、三个 `counts` 都为 `null`。程序不会把10天结果外推成30天数据。本期已按用户需求明确选择10天，由上方回放处理器生成对应指标；未来切换30天时需补齐源覆盖并同步调整组件观察期与界面标签。

`--coverage-start` / `--coverage-end` 是源系统实际导出查询区间的声明，必须来自导出条件或可靠源系统记录。它不是随意填长的日期标签。程序要求该区间完整包含分析窗口，且所有数据行的原始收款日期均在该声明范围内；违反任一条件会输出不可用。没有订单的日期可以是零销售日，前提是源系统确实完整查询了该日；仅从“最早/最晚有交易日”无法证明导出完整性。当前 9 月 24 日～10 月 3 日的文件不能声明已经覆盖 9 月 4 日～10 月 3 日。

只读取原始 `收款日期`。不使用文件名日期、导出时间、系统今天或记账日期替代购买日。日期单元格、日期格式的 Excel 单元格及明确的年月日文本均可识别；没有日期格式的数字不猜测为 Excel 日期。`updatedAt` 是处理时间，带 `+08:00` 时区，不代表新的交易发生。

## 计算口径

- 有效订单：原始 `实收金额 > 0` 的订单头，以 `(门店编码, 收款日期, 流水号)` 为完整业务键。商品行、数量、金额总和都不能代替订单次数。
- 身份：只用非空稳定 `会员编码`，不按会员姓名、电话匹配，也不推测匿名顾客身份。空编码的正支付订单只进入匿名覆盖诊断，不进入会员指标分子或分母。
- `identifiedCustomers`：窗口内至少一个有效订单的去重会员数。
- `purchaseOrders`：上述已识别会员在窗口内的有效订单总数。
- `repeatCustomers`：窗口内至少两个不同有效订单的会员数。允许同日多笔订单，因此表示窗口内多次下单，不表示再次到店或首购后 30 日复购概率。

页面可由 `purchaseOrders / identifiedCustomers` 得到**30 天购买会员人均订单次数**，由 `repeatCustomers / identifiedCustomers` 得到**30 天购买会员多次下单占比**。它们只描述可识别会员，不代表全部消费者。分母为 0 时，页面显示 **—**，不要做除零或展示假的 0%。

非正支付订单不算新增购买。当前退款没有可用原销售关联，因此这里只计算正支付订单频次，不把后续退款回冲到原订单；无法证明某个会员订单最终是否全额退款。需要“扣除全额退款后的有效购买”口径时，应补原销售单号、退款单号和部分/全额退款关系，另行调整处理规则。

相同业务键、相同会员编码和相同实收金额的重复行折叠一次；会员或金额不同则整份计算不可用。退款和正支付记录也先做冲突验证，再做正支付筛选，不能用筛选掩盖重复冲突。姓名等展示字段不参与身份匹配或次数计算。

字符串身份保留原样及前导零。数值身份只接受可以精确表示的整数，不猜补 Excel 显示的前导零；数字/文本混用且可能指向同一编号时整份计算不可用，要求源端统一输出身份为文本。没有稳定消费者身份的交易不能通过姓名或每笔匿名交易生成一个虚构顾客。

## 输出与运行

输出契约为 `{status, sourceKind:"actual", updatedAt, window:{start,end,days,complete}, counts:{identifiedCustomers,purchaseOrders,repeatCustomers}}`，附加 `diagnostics` 仅含行数、覆盖区间、匿名/会员正支付订单数、负支付订单数、折叠数量及非敏感错误码。输出不包含订单号、会员编码、姓名、电话、原始行值或源文件路径。真实数据范围不足或数据冲突时，所有指标计数为 `null`。

文件在临时文件完整写入后原子替换，避免页面读到一半的 JSON。正常计算退出 0，不可用数据退出 2，文件写入失败退出 1。stdout/stderr 只输出状态及固定错误码，不打印源行值或异常堆栈。源表保持原样。

后端定时任务或 ERP 导出完成步骤可调用该 CLI，并将结果放到页面使用的 `data/consumer-metrics.json`。刷新页面数据并不能增加原始历史覆盖；获得足够源数据后重新生成，页面才会显示真实值。请保留每次导出完整区间与处理结果的私有审计记录。

## 当前网页接入

`ConsumerMetrics`组件已接入消费者分析模块，默认每60秒读取同站`data/consumer-metrics.json`。在大屏配置的“基础配置 → 消费者分析数据”可更换为HTTPS汇总地址或调整间隔，配置只存当前浏览器。只读取JSON聚合数据，不接收源Excel、会员明细或API密钥。

组件默认仍严格要求上海当前业务日结束的完整30天；本期实例明确配置10天、允许真实历史窗口，接收已提供期间汇总。数据不足、计数无效、没有可识别购买会员时显示“—”。有效数值变化时只高亮变化的数字；请求失败保留最后汇总并在配置/悬停标明读取失败。回放层与实际历史缓存分离，60秒读取不会覆盖正在回放的计数；上海跨日会重新开始同一批历史回放，不伪造新的购买。未来当前30天模式的跨日失效保护保持可用。

`file://`默认读取`consumer-metrics-data.js`、`consumer-replay-data.js`随包快照，本地也能让内置回放推进指标。自动获取新源数据需使用托管网页及更新后的JSON或HTTPS接口。静态网页不会自动读取新的本机Excel或从ERP拉取订单。私有处理端生成JSON后更新网站数据文件；为保持单文件、内置订单及回放聚合一致，也需同步编译并发布。
